**4. How do you design a robust, scalable test automation framework?**
Key components: 
	1. Page Object Model (or Screenplay pattern for larger enterprise suites) for maintainability; 
	2. a Driver factory using ThreadLocal<WebDriver> for thread-safe parallel execution; 
	3. a config/properties management layer (YAML/properties + environment overrides); 
	4. a reporting layer (ExtentReports/Allure); 
	5. TestNG: listeners for screenshots-on-failure (TestNG `ITestListener`); a retry-analyzer for flaky tests; data-driven testing via TestNG DataProviders or external JSON/Excel; 
	6. CI/CD integration (Jenkins/GitHub Actions) with Selenium Grid or cloud grids (BrowserStack/Sauce Labs/LambdaTest) for cross-browser runs; 
	7. and clean separation of test logic from framework utilities.

Framework Design (this is where 10-YOE interviews focus most)

### Q6. Walk me through how you'd design a Selenium framework from scratch.
**Answer — talk through these layers:**
1. **Driver Management layer** 	— `ThreadLocal<WebDriver>` for parallel-safety (see Q9).
2. **Page Object Model layer**	— POM design pattern (page = class, elements = fields, actions = methods), one class per page/component.
3. **Test layer** 				— TestNG-Test cases classes, only business flow, no locators/waits.
4. **Utility layer** 			— WaitUtils, ExcelUtils, JsonUtils, ScreenshotUtils, ExtentReportManager.
5. **Data layer** 				— external test data (Excel/JSON/DB) via DataProvider — no hardcoded data in tests.
6. **Config layer** 			— `config.properties` per environment (QA/Stage/Prod), loaded via a Singleton `ConfigReader`.
7. **Reporting layer** 			— Extent Reports / Allure + screenshots on failure.
8. **CI/CD layer** 				— Jenkinsfile/GitHub Actions triggering via Maven, with parallel Grid execution.
9. **Listener layer** 			— TestNG `ITestListener`/`IRetryAnalyzer` for retries, logging, reporting hooks.

This is usually called a **Hybrid Driven Framework** (POM + Data-Driven + Keyword elements + BDD on top with Cucumber, if applicable).
